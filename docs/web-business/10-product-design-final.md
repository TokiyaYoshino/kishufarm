## 02. 目標の作り方が変わる — フローからストックへ

月商30万円を、定価別に逆算する（1件あたり22時間、成約率40%と仮定）。

| 定価 | 必要な新規/月 | 必要な商談/月 | 時給換算 |
|---|---|---|---|
| **30万円** | **1.0件** | **2.5件** | 13,600円 |
| 45万円 | 0.67件 | 1.7件 | 20,500円 |
| 58万円 | 0.5件 | 1.3件 | 26,400円 |

09章の営業設計は**月1.6〜3.5件の商談**が想定上限で、しかも紹介が主軸。
**定価30万円を制作費だけで回すと月2.5件の商談が要り、紹介チャネルでは持たない。**

### だから保守をストックとして積む

| 保守の社数 | ストック（月1.5万円） | 必要な新規/月 |
|---|---|---|
| 0社 | 0円 | 1.0件 |
| 5社 | 7.5万円 | 0.75件 |
| 10社 | 15万円 | 0.5件 |
| **20社** | **30万円** | **0件** |

**20社まで積めば、制作ゼロでも月商30万円に届く。**
これは単価58万円のフロー型には無い性質で、定価30万円を選ぶ理由そのものになる。

**目標指標を「今月の成約数」から「保守契約の純増数」に置き換える。**
解約が出れば相殺されるので、仮に年15%解約なら20社の維持に年3社の新規が必要、という見方をする。

### 定価30万円を選ぶもう一つの理由

モニター価格15万円を置くと決めた以上、**15万 → 58万は4倍で説明がつかない。15万 → 30万なら2倍で「モニター終了」で通る。**
モニターを挟むなら、定価は30万円のほうが一貫している。

## 03. 商品構成

| | 内容 | 価格 |
|---|---|---|
| **本体** | 静的サイト（5〜8ページ）＋Googleビジネスプロフィール初期設定＋構造化データ（JSON-LD）＋既存素材の選定・配置＋撮り方ガイド | **30万円**（モニター15万円） |
| **必須** | 月額保守＋MEOレポート（自動生成） | **月1.5万円** |
| OP | 枠予約の自動化（GAS） | 10〜15万円 |
| OP | EC・予約SaaSの設定代行（STORES / BASE / STORES予約 等） | 5万円 |
| — | 撮影 | **受けない。**カメラマン紹介・実費 |
| — | 決済・EC本体 | **受けない。**STORES / BASE を紹介 |

### 3プランを畳む理由

1. 2:4:4 の想定は**売上の8割を未実績プランに置いている**。売れた瞬間に作れない
2. 15〜60万円という幅は商談で必ず下に流れる。**紹介主軸なら1本値のほうが強い**
   （紹介の利点は価格交渉が起きにくいことなのに、幅を自分で用意すると打ち消す）
3. 下限15万円のPLAN01を残すと、月商30万円に月1件必要になり、営業が持たない

### 30万円の範囲は22時間以内に厳格に切る

時給13,600円が成り立つのは22時間だから。30時間に膨らむと10,000円、40時間で7,500円。
**58万円と違い、30万円は膨らみに耐えられない。**範囲外はすべてオプションにする。

### 撮影を外す代わりに置くもの

がめ吉が Unsplash の仮画像のまま止まっている以上、**写真が無いと公開できない問題は残る**。代替は3つ。

1. **撮り方ガイド1枚を渡す**（スマホでOK・自然光・撮ってほしい8カットのリスト・縦横比）。原価ゼロで効果が最も大きい
2. **既存素材の選定・補正・配置は本体に含める。**ターゲット像は「Instagramはやっている個人店」なので素材はたいてい既にある
3. **カメラマンは紹介だけ**（手配はする、費用は店が直接払う実費。3〜5万円が目安）

## 04. 静的で確定する — 動的にしない理由

| | 静的（Cloudflare Pages / Vercel） | 動的（Next.js + Supabase + microCMS） |
|---|---|---|
| クライアントの月額原価 | **ドメイン代のみ** | Supabase 3,800円＋microCMS 9,800円＝**月13,600円** |
| 月1.5万円の保守 | ほぼ全額が粗利 | **ほぼ全額が原価**。粗利が消える |
| 運用 | 落ちる要素がほぼ無い | Supabase無料枠は1週間アクセスなしで停止。設計書自身が「GitHub Actions Cronでping」という回避策を書いている＝**運用負債** |
| 更新 | こちらが直す | CMSを入れても店主は使わない（がめ吉のREADMEも更新手段が `lib/site.ts` を編集） |

**線引き：サイト本体は静的。動的が要るのは予約と決済だけ。**
そして予約は GAS で受け、決済は持たない。結果として**動的サイトを自前で持つ理由が消える**。

例外は、メニューが頻繁に変わる飲食店など更新頻度が高いケース。
その場合も microCMS ではなく**スプレッドシート＋ビルド**（店主が触れて、無料で、GASと同じ土俵）。

## 05. 予約と決済の線引き

原則：**止まっても店が困らないものだけ、こちらが責任を持つ。**

- サイトが止まる → 困るが致命的でない
- MEOが止まる → 数字が出ないだけ
- **予約が止まる → その日の営業が止まる**
- **決済が止まる → お金の事故**

### 決済・EC — 持たない

1. `gas-ops/docs/fit-criteria.md` 自身が「PCI DSS等の厳格な準拠要件があり、Stripe決済リンクのような簡易連携では不十分」なら向かないと書いている
2. **資金決済法の前払式支払手段（回数券EC）は TODO E5 で未確認のまま。**法令リスクを自分で抱える理由がない
3. 特商法表記・返品・キャンセル・チャージバックの問い合わせが全部こちらに来る。月1.5万円の保守で受けられる範囲を超える
4. 物販なら在庫と発送がついてくる。制作の仕事ではない

→ **STORES / BASE を紹介し、サイトから導線を作る。**設定代行として5万円を取れるので、売上も落ちない。

### 予約 — 枠予約だけ自前

| 業種・形態 | 判断 |
|---|---|
| 教室・イベント・回数制・整体の時間枠 | **GASで自前。**原価ゼロ・粘着性が高く、ストックの本命 |
| 美容室の指名・席管理 | **既存SaaS。**`reservation-booking` の README 自身が「残り1枠に同時応募で取りこぼし・二重受付」と書いている。予約ミスは即クレーム |
| 飲食の席予約 | SaaS寄り。当日キャンセル・人数変更が多く運用が重い |

**「うちで作れます」より「それはSTORESのほうが安くて確実です」のほうが、
保守の断絶を売りにしている以上は一貫している。**`fit-criteria.md` の方針の延長でもある。

## 06. 保守の中身と、その自動化

月1.5万円で何を出すのか。そして**費用をかけずにどこまで自動化できるか**。

### 技術面

| やること | 自動化 | 手段（すべて無料枠） |
|---|---|---|
| 死活監視 | **完全自動** | UptimeRobot 無料50モニター・5分間隔 |
| SSL更新 | **不要** | ホスティング側が自動 |
| リンク切れ（地図・Instagram・外部） | **完全自動** | GitHub Actions で週1チェック |
| ビルド失敗の検知 | **完全自動** | ホスティングの標準通知 |
| 依存パッケージ更新 | **半自動** | Dependabot がPRを立てる。CIが通れば1クリック |
| 表示崩れ | **半自動** | GitHub Actions ＋ Playwright で月1スクショ、前月と差分比較 |
| **問い合わせフォームの到達確認** | **自動化可能（要自作）** | GASで週1テスト送信 → 受信確認 → **失敗時のみ通知** |

> **フォームの到達確認は必ず入れること。**保守で唯一、黙って壊れて店が損をするのがここで、
> 気づかないまま3ヶ月、が普通に起きる。

### 集客・MEO面

| やること | 自動化 | 手段 |
|---|---|---|
| **GBPの表示回数・ルート検索・通話数** | **完全自動** | **Google Business Profile Performance API（無料）** をGASから叩いてシートに日次記録 |
| **検索クエリ・表示回数・CTR・掲載順位** | **完全自動** | **Search Console API（無料）** 同上 |
| 構造化データの検証 | **半自動** | JSON-LDをパースして必須項目チェックをGitHub Actionsで。Rich Results Test に公式APIは無い |
| **月次レポートの作成・送付** | **完全自動** | シートのデータからGASで月初に生成 → 店主とこちらにメール |
| AI検索の引用チェック | **手動のまま** | 3〜5クエリを目視。月5分 |
| レビュー返信 | **やらない** | 店主の仕事。文面テンプレを渡すまで。こちらが書くと「中の人」を騙ることになる |

### 全体像

```
UptimeRobot（無料）      → 5分間隔の死活監視
GitHub Actions（無料）   → 週1リンク切れ / 月1スクショ差分 / 構造化データ検証
Dependabot（無料）       → 依存更新PR
GAS（無料）
  ├ 日次 Search Console API   → スプレッドシート
  ├ 日次 GBP Performance API  → スプレッドシート
  ├ 週1  フォーム疎通テスト     → 失敗時のみ通知
  └ 月初 レポート自動生成       → 店主へメール
```

**人に残るのは月15〜30分／件。**AI検索の引用チェック、レポートに所感を1〜2行足す、依存更新PRのマージ判断。

→ **20社 × 30分 ＝ 月10時間で、ストック月30万円。**保守が増えても制作の時間を食わない。

### 先に潰すべきこと

1. **Google Business Profile API はアクセス申請が必要。**承認まで数週間かかることがある。**自動化の中核なので最優先で申請する**
2. **Search Console と GBP の権限付与を、納品手順に組み込む。**後から頼むと面倒がられる
3. **自動化を作る工数が先に要る**（GAS＋GitHub Actions で2〜3日）。**モニター1件目の前に作れば、1件目から実測データが溜まる**

> **副産物：この自動化はそのまま gas-ops の5つ目のモジュールになる。**
> 自社で20社分回してから商品化するので、「作ったことがないものを売る」問題が起きない。
> さらに、毎月レポートが自動で届く関係は、09章の「保守は収益より接点として効く」を手間ゼロで実現する。

## 07. モニター価格の設計（実績5件目まで）

初期費用15万円・月額は定価のまま、という形を推す。

### なぜ「安くする」ではなく「定価から割り引く」なのか

09章で「紹介は価格交渉が起きにくい」と整理したが、**裏を返すと前の価格がそのまま伝播する**。
紹介元は「あそこは15万円でやってくれた」と言う。
**主軸が紹介チャネルなので、安い実績を紹介で増やすと、安さが複製される。**

→ 見積書に**定価と割引額を両方書く**。これをやらないと15万円が定価として世に出る。

```
サイト制作＋Googleビジネスプロフィール初期設定      定価 300,000円
  モニター価格（先着5社・実績掲載にご協力いただける方）  −150,000円
  ご請求額                                        150,000円
```

### 月額は下げない

初期費用は一度きりなので割引の理由がつく。**月額は毎月発生するのでアンカーが固定される。**
月6,000円で5件入れると6件目に1.5万円が出せず、既存5件を後から上げるのは実務的にほぼ無理。
どうしても下げるなら**金額ではなく期間で引く**（3ヶ月無料、以降1.5万円）。

加えて、月6,000〜1万円には**障害対応と問い合わせが青天井**という落とし穴がある。
質問の多い店が1つ混じると即座に崩れる。

### 安くする代わりに回収するもの（契約またはモニター規約に入れる）

5件の目的は売上ではなく実績なので、取るものを取らないと目的を達成しないまま安く売っただけになる。

1. 制作実績としてサイト名・スクリーンショットの公開許可
2. フッターへの制作クレジット（チャネルF）
3. **3ヶ月後に成果の数字を共有してもらう**（GBPインサイト、問い合わせ件数）
4. 紹介1件のご協力
5. こちら側での実働時間の記録（検証項目⑤ / TODO C1 の実測）

> 特に3番。実績ページは「具体的な成果が示されているもの」が信頼される（04章）。
> **「問い合わせが倍増」と書けるかどうかは、この約束を最初に取れたかで決まる。**

### モニター価格に含める範囲

| 含めるもの | 想定工数 | 15万円での時給 |
|---|---|---|
| 静的サイト＋GBP初期設定 | 実装8h＋コンテンツ回収10h＋打ち合わせ4h ＝ **22h** | **約6,800円** |
| ＋GAS予約 | ＋20h ＝ **42h** | **約3,570円** |

外注想定が3,500円/h（04章）なので、**GAS予約まで入れると自分を外注単価で使うことになる。**
→ **モニターに含めるのは「静的サイト＋MEO初期設定」まで。GAS予約は別見積り。**

### 月商の推移

| | 月商 |
|---|---|
| モニター1件目 | 15万＋1.5万 ＝ 16.5万円 |
| モニター5件目 | 15万＋7.5万 ＝ 22.5万円 |
| 通常価格移行後（30万×1件＋保守7.5万） | 37.5万円 |

**5件のあいだは月商30万円に届かない。**期間は織り込んでおく必要がある。
がめ吉・ANUHAIR をこの5件に数えるかで、残り3件か5件かが変わる。

### 独自ドメインメールの整理

- **HPにドメインを設定すること自体は無料**で、Workspace とは無関係（ホスティング側のカスタムドメイン機能）
- **Gmailに独自ドメインのメールボックスを持たせるなら Workspace が必須。**
  かつての「Google Apps 無料版」は新規受付も無料レガシー版も終了している（kishufarm.com はこの形で運用中）
- 無料で組む手段（Cloudflare Email Routing で受信転送＋Gmailの「他のメールアドレスを追加」で送信、Zoho Mail 無料プラン等）はあるが、
  **顧客案件では推奨しない。**設定が入り組み、メールが届かない疑いが出るたびに問い合わせが来る。
  **月1,000円払って Workspace にするほうが、サポートコストで見れば安い**

### 注意点

**① Vercelの無料プランは商用利用が制限されている可能性がある — 最優先で確認**

Vercel の Hobby プランは非商用・個人利用向けという位置づけで、**店舗サイトは商用に当たる**。
該当すると Pro（月$20≒3,000円）が必要になり、「月300円で運用できます」という説明が崩れる。
**がめ吉珈琲が既にVercelなので、実在の案件の話でもある。**

→ 静的サイトなら **Cloudflare Pages**（商用利用可・無料）への移行を推す。静的書き出しならそのまま乗る。
ここが変わると `01-briefing.md` 第5章のコスト表も書き換えになる。

**② Gmailの1日あたり送信上限**

GASから予約確認・リマインドを送る場合、**個人Googleアカウントは1日100通程度、Workspaceは1,500通程度**が上限。
`fit-criteria.md` の想定（月数十〜数百件）なら問題ないが、
**1日100件を超える教室・イベント系は Workspace が必須**になる。fit-criteria に1行追加すべき。

**③ LINE公式アカウントの料金改定**

無料枠の通数も有料プランの価格も変わってきた経緯がある。
「LINE通知を入れると月いくら」は商談で必ず聞かれるので、提示前に現行の料金ページを見ること。

## 09. 契約に足すべき項目

`08-contract-templates.md` の条項ドラフトに無く、追加が必要なもの。

1. **ドメインは必ず店舗名義で取得・契約する。**制作側の名義で取ると、離れるときにドメインが人質になる。
   「作って終わりにしない人が近くにいる」を売りにする以上、**逆をやらない姿勢を先に明示する**ほうが強い
2. **Googleアカウント（GBPのオーナー権限を含む）も店舗名義。**こちらは「管理者」ではなく「権限を付与された側」に立つ
3. **Workspace を導入する場合も管理者は店舗。**メールは業務の生命線で、これを握ると「止まったら営業が止まるもの」を背負うことになる
4. **モニター規約**（07章の回収項目5点）
5. **保守の範囲**（06章の表を契約書に貼る）と、範囲外の扱い
